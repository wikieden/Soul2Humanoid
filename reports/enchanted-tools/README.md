## 二、硬件架构

### Miroki 机器人规格

| 参数 | Miroki |
|------|--------|
| **身高** | ~120-130 cm（较小体型，非成人尺寸） |
| **体重** | ~30-40 kg |
| **移动方式** | **轮式底座**（非双足），带平衡系统 |
| **手臂自由度** | ~6-8 DoF（双臂） |
| **末端执行器** | 定制化夹爪/手指，适合轻量物品传递 |
| **头部** | 表情显示屏（LED/屏幕），可表达情感 |
| **传感器** | 深度相机、麦克风阵列、触摸传感器、轮式里程计 |
| **续航** | ~6-8 小时 |
| **计算单元** | 嵌入式 ARM + 可选边缘 AI 加速 |

### 设计哲学

- **小巧亲和**：刻意选择较小体型和轮式移动，降低用户的恐惧感
- **表情交互**：头部显示屏可呈现丰富的表情，增强社交属性
- **安全优先**：轻量级设计、软体材料包裹，适合与老人/儿童近距离互动
- **静音运行**：轮式移动比双足安静得多，适合医院/养老院环境

## 三、AI 与软件架构

### 核心特点：社交 AI + 服务自动化

Miroki 的 AI 重点不在**物理操作的灵巧性**，而在**人机交互的自然性和任务执行的可靠性**：

```
┌─────────────────────────────────────────┐
│  对话与情感交互层                          │  ← LLM + 情感识别 + 语音合成
├─────────────────────────────────────────┤
│  任务管理层                               │  ← 导航、物品递送、提醒服务
├─────────────────────────────────────────┤
│  感知层                                   │  ← 人脸/情绪识别、物体检测、SLAM
├─────────────────────────────────────────┤
│  运动控制层                               │  ← 轮式导航、手臂轨迹规划
└─────────────────────────────────────────┘
```

### 对话与情感交互

- **大语言模型 (LLM)**：集成主流 LLM（可能是 GPT 或自研）进行开放域对话
- **情感识别**：通过视觉（面部表情）和语音（语调分析）识别用户情绪状态
- **情感表达**：头部屏幕显示表情符号/动画，语音语调可调整
- **多语言支持**：针对欧洲市场，原生支持法语、英语、德语等

### 导航与定位

- **轮式 SLAM**：基于激光雷达/深度相机的 2D/3D SLAM
- **语义地图**：理解环境中不同区域的功能（病房、休息室、护士站）
- **自主避障**：动态行人检测和路径重规划
- **电梯/门禁集成**：与建筑设施联动，实现跨楼层服务

### 操作能力

- Miroki 的**操作能力相对有限**：主要是**递送小物品**（药品、文件、水杯）
- 使用简单的**预定义抓取策略**，而非通用灵巧操作
- 操作任务失败时，可呼叫人类协助（语音或通知系统）

## 四、数据策略

### 数据来源

| 来源 | 描述 |
|------|------|
| **仿真数据** | 导航、路径规划的仿真训练 |
| **试点现场数据** | 医院/养老院部署中的交互数据 |
| **遥操作调试** | 工程师远程监控和干预 |
| **LLM 预训练** | 利用公开大模型，无需自研基础模型 |

### 数据飞轮

Enchanted Tools 的**数据飞轮较弱**，原因：
- 场景相对静态（固定建筑环境），导航数据复用价值有限
- 对话数据可积累，但主要依赖第三方 LLM 的能力迭代
- 物理操作数据量小，且操作任务简单

公司的**核心壁垒**更多在于**场景理解**、**产品定义**和**客户渠道**，而非数据驱动的技术迭代。

## 五、商业化与竞争格局

### 目标场景

| 场景 | 应用方式 |
|------|---------|
| **医院** | 药品/样本递送、患者引导、信息查询 |
| **养老院** | 陪伴互动、用药提醒、紧急呼叫、物品递送 |
| **酒店/接待** | 访客引导、信息咨询、简单接待 |
| **教育** | 儿童陪伴、基础教学辅助 |

### 商业模式

- **设备销售**：一次性购买 + 年度服务合同
- **租赁模式**：按月/年租赁，包含维护和软件更新
- **解决方案集成**：与医院信息系统 (HIS)、养老管理平台集成

### 核心竞争优势

| 优势 | 说明 |
|------|------|
| **Pepper 团队经验** | 深刻理解社交机器人的设计陷阱和用户需求 |
| **欧洲市场先发** | 针对欧洲医疗/康养市场的本地化优势 |
| **亲和力设计** | 小巧、可爱、安静，比大型工业人形更适合服务场景 |
| **轮式可靠性** | 轮式移动比双足成熟得多，维护成本低 |
| **成本可控** | 小型化+轮式设计，硬件成本显著低于双足人形 |

### 竞争劣势

| 劣势 | 说明 |
|------|------|
| **技术天花板** | 不做双足、不做灵巧手，长期技术壁垒有限 |
| **LLM 依赖** | 核心对话能力依赖第三方，差异化弱 |
| **场景局限** | 医院/养老市场的付费意愿和预算有限 |
| **Pepper 阴影** | 市场可能对"又一社交机器人"持谨慎态度 |

## 七、总结与展望

### 技术路线判断

Enchanted Tools 代表了人形机器人领域的**"服务派"**——不追求最强的物理能力，而是追求最合适的场景匹配和用户体验。

- **短期（2024-2026）**：在欧洲医疗/康养市场建立标杆案例，验证商业模式
- **中期（2026-2028）**：如果试点成功，可能成为服务场景人形机器人的领先者
- **长期**：面临被更通用的轮式+手臂平台（如未来降本的通用人形）替代的风险

### 与 Pepper 的对比：能否避免同样的命运？

Pepper 的失败原因：
1. 功能过度承诺（"能读情绪"实际很基础）
2. 维护成本高，故障率不低
3. 没有找到真正的刚需场景
4. 软银激进的销售目标导致渠道压货

Enchanted Tools 的应对：
- **更务实的功能定义**：不强调"情感"，强调"递送+提醒+陪伴"的实用组合
- **更聚焦的场景**：深耕医疗/养老，而非泛化的"接待"
- **欧洲本地服务**：避免跨大区支持的复杂度

### 核心关注点

1. **医院/养老院试点的真实运营数据**：每日任务完成率、用户满意度、故障率
2. **与 Pepper 的本质差异**：是否真的解决了 Pepper 没解决的痛点
3. **成本控制**：小型轮式机器人的 BOM 成本能否压到可盈利水平
